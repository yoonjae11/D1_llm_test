# Main Azure Function App architecture

`azure_function_main_app` is the deployable Sensei backend that owns the
Telegram conversation endpoint, personal sensor-data analysis, user-configured
alerts, scheduled reports, system STEPS alerts, conversation state, and the
service boundaries used to reach Azure OpenAI, Azure Data Explorer (ADX), and
Azure Table Storage.

## Runtime entrances

### User-initiated conversation

```text
Telegram webhook
  -> chatbot.entrypoint.handle_user_message
  -> chatbot.services.sensor_analytics.run_sensor_analytics_graph
  -> chatbot.graph.build_graph
  -> chatbot.graph.workflow
  -> the D1-D4 registered domain subgraphs and operational responders
  -> policies, prompts, and service ports
  -> provider adapters and Azure clients
```

Slash commands, registration, interactive profile collection, Withings linking,
and guided threshold setup can be handled by the Telegram/function layer before
an ordinary message reaches LangGraph.

### System-initiated conversation

Initial proactive notifications are not generated by LangGraph:

- `chatbot.proactive.threshold_monitor` owns threshold-breach messages and scheduled daily
  reports.
- `chatbot.proactive.system_steps_alert` owns System STEPS outlier evaluation and its
  deterministic message.
- `chatbot.episode_service` records the proactive episode, suspends any active
  reactive episode when configured, and stores follow-up context.

When the user replies, the Telegram transport calls the same user-message
entrypoint. `chatbot.nodes.common.prepare_context.prepare_context` restores the
proactive episode and the remaining reply is processed by the shared D1-D4
orchestration graph. A daily report can seed a follow-up plan; other proactive
messages supply system episode context to the domain planner.

## Canonical package ownership

- `chatbot/graph/state.py` defines `AgentState` and state-oriented message
  helpers.
- `chatbot/graph/workflow.py` owns the six-stage top-level graph only.
- `chatbot/nodes/common/` owns hydration, aggregation, final responses and persistence.
- `chatbot/nodes/planning/` owns the combined intent/domain plan, deterministic
  greeting fast path, route mapping and DAG validation.
- `chatbot/nodes/orchestration/` owns the uniform D1-D4 runner registry and scheduler.
- Each `chatbot/nodes/d*/workflow.py` owns its actual LangGraph subgraph. D1
  query implementations live in `d1_sensor_data/`; D2 Advisor steps live in
  `d2_coaching_strategy/`; D3/D4 each own an explicit placeholder node.
- `chatbot/nodes/operational/` owns onboarding, capability and configuration responses.
- The `chatbot/nodes/` root contains no executable node modules. Every node is
  imported from its one canonical ownership package.
- `chatbot/policies/` owns deterministic, provider-independent domain and safety
  rules.
- `chatbot/prompts/` mirrors the model-calling owner: `planning/`,
  `d1_sensor_data/`, `d2_coaching_strategy/`,
  `common/generate_final_response/`, `operational/`, and
  `proactive/threshold_monitor/`. Typed output contracts remain in
  `chatbot/schemas/`, and each owning node assembles its runtime messages.
- `chatbot/proactive/` owns initial alerts and daily reports outside the graph.
- `chatbot/i18n/` owns deterministic English user-visible text and stable compatibility keys.
- `chatbot/services/` defines application boundaries and provider ports.
- `chatbot/adapters/` connects those ports to the established LLM, ADX, and
  storage implementations.
- `chatbot/schemas/tool_result.py` defines the transport-neutral
  `ChatbotResponse` returned by the public entrypoint.

## D1-D4 orchestration graph

```text
START -> prepare_context -> plan_domain_execution -> execute_domains
      -> aggregate_domain_results -> generate_final_response
      -> persist_trace_and_context -> END
```

D1 physically owns the existing data planner, KQL generation, guard, bounded
repair, ADX executor and result conversion. The established policies and
service ports are reused. D2 is a four-node LangGraph: context preparation,
one typed strategy model call, deterministic validation and result wrapping.
D2 controls applicability, objective, COM-B, supported BCT selection, MI/SDT
and interaction depth. Only the common response node writes the final answer.

Plans declare `selected_domains`, `domain_requirements`, `dependencies`,
`execution_stages` and `early_exit_conditions`. The deterministic validator
rejects unsupported domains, malformed graphs, cycles, repeated executions,
invalid dependency order and more than three stages. Same-stage tasks execute
with isolated snapshots; declared dependency wrappers flow to later stages.
All four `run_d*` functions return `DomainRunOutput(result, state_updates)`.

D3 and D4 are selectable, explicit model-free graphs. D3 retrieves only from
the versioned, hash-validated approved health corpus and applies deterministic
safety/abstention policy. D4 resolves current-session references, latest values,
and superseded turn IDs, and requests clarification when evidence is absent.
Any required dependency whose status is not `success` blocks the downstream
runner with `blocked_dependency`. Optional failures remain visible as status
and missing-information evidence; they are never treated as successful retrieval.
Operational and sensor error/no-data responses retain their established priority.

See [graph details](chatbot/graph/README.md), the
[node ownership guide](chatbot/nodes/README.md), and the
[prompt inventory](chatbot/prompts/README.md).

## KQL construction and safety boundary

These similarly named components have deliberately different responsibilities:

| Component | Responsibility |
|---|---|
| `chatbot/policies/kql_generation.py` | Pure deterministic construction of source-aware personal-data KQL and bounded deterministic fallback queries. It is not a graph node. |
| `chatbot/nodes/d1_sensor_data/generate_sensor_query.py` | Selects deterministic generation, the optional configured LLM candidate path, or the hard deterministic fallback. It does not authorize execution. |
| `chatbot/policies/kql_safety.py` | Pure read-only policy for table allowlists, user scoping, bounded time ranges, result bounds, unsafe syntax, and deterministic syntax repair. |
| `chatbot/nodes/d1_sensor_data/guard_sensor_query.py` | Applies the safety policy and emits `execute`, `repair`, or blocked status. |
| `chatbot/nodes/d1_sensor_data/repair_sensor_query.py` | Performs a bounded model repair and always returns the candidate to `guard_sensor_query`. It never executes KQL. |
| `chatbot/nodes/d1_sensor_data/execute_sensor_query.py` | Executes an authorized query through the ADX service and normalizes results. ADX-error retries are limited to queries rebuilt by the trusted deterministic policy. |

An arbitrary or model-produced KQL candidate cannot route directly to ADX.
Only `guard_sensor_query` can send the normal graph path to
`execute_sensor_query`, and every model repair is re-guarded. The configured
repair-attempt limit prevents an unbounded cycle.

## Dependency rules

1. Function and Telegram transports call application entrypoints; they do not
   construct graph state or register graph edges.
2. `graph/workflow.py` owns the six top-level stages; D1-D4 encapsulate
   domain execution while reusing the existing provider and storage boundaries.
3. Nodes read and return partial `AgentState` dictionaries, load their model
   resources, call pure policies, and use service ports for external I/O.
4. Policies do not import graph nodes, Azure SDKs, provider clients, or function
   blueprints.
5. Model-produced KQL remains separate from authorization and ADX execution.
6. System notification producers remain outside the reactive graph; replies
   re-enter through the common `prepare_context` node, which restores durable
   conversation and proactive-episode context.
7. Environment-variable names, Azure routes, storage entities, ADX source
   semantics, and the `ChatbotResponse` contract must remain stable during
   internal refactoring.

See `docs/refactoring/` for the historical baseline, canonical target, and
completed path migration record.
